## PayPal Company, Product Ecosystem & Engineering Stack Forensics

To win **Technological Implementation (20% — Tie-Breaker #1)** and **Best Use of PayPal + AI ($5,000)**, our architecture directly mirrors and integrates PayPal's real internal production stack and open-source developer tools [S18–S35, S63–S68]:

### 1. Core Application Frameworks & Polyglot Runtime Stack
- **Java (`JDK 17/21`, `Spring Boot`, `PayPal Raptor`)**: **Raptor** is PayPal's internal enterprise Java microservices framework built on Spring Boot and Netty/JAX-RS, powering thousands of core ledger, settlement, risk orchestration, and compliance services with standardized mTLS, circuit breaking, and OpenTelemetry tracing [S22].
- **Node.js & TypeScript (`Kraken.js`, `Zoid`, `PayPal Web SDK v6`, `React 19`, `Next.js 15`)**: PayPal pioneered enterprise Node.js adoption and open-sourced **Kraken.js** (`github.com/krakenjs/kraken-js`, providing `confit` environment config, `lusca` CSRF/CSP/HSTS security, and `makara` i18n), **Zoid** (`github.com/krakenjs/zoid`, the cross-domain iframe/popup component protocol that powers the **PayPal JavaScript SDK** Smart Payment Buttons across millions of sites), and **PayPal Web SDK v6 (`web-sdk/v6/core`)** (which requires awaiting the asynchronous `.start()` Promise before mounting payment components and enforces strict mutual exclusivity between `clientId` and `clientToken`) [S23, S24, S66].
- **Golang & C++ (`JunoDB`, `RocksDB`, `Envoy`)**: Go powers PayPal's high-concurrency infrastructure control planes and **JunoDB**, while C++ powers low-level storage engines (`RocksDB`) and **Envoy** powers PayPal's service mesh and **Cosmos LLM Gateway** [S20, S21, S26].
- **Python (`PyTorch`, `PyTorch Geometric`, `gators` [Polars + ONNX Runtime], `FastAPI`, `Ray`, `Spark`)**: Primary language for ML model training, **Graph Neural Network (GNN)** fraud inference, PayPal's open-source **`gators`** (`github.com/paypal/gators`) Polars + ONNX Runtime feature engineering library, and **Cosmos.AI** pipelines [S26, S27, S67].

### 2. Planet-Scale Data, Storage & Event Streaming Infrastructure
- **`JunoDB` (`github.com/paypal/junodb` — Apache-2.0 Open Source)**:
  - Authored by **Yaping Shi, Xuetao Li, Kamlakar Singh, Mukundan Narayanan**, and the PayPal Data Platform team [S20, S21].
  - Serves **350+ billion requests per day** across PayPal (with individual clusters exceeding 200 storage nodes and 100B+ req/day) at **99.9999% (six 9s) availability** and **single-digit millisecond latency** [S20, S21].
  - Rewritten from single-threaded C++ to **Golang** for multi-core goroutine concurrency, backed by **RocksDB** for persistent on-disk TTL storage and **etcd** (`clustercfg`) for shard topology management across a 3-tier decoupled architecture (`junoclient` SDKs in Java/Go/Python/Node.js → stateless `proxy` on `:5080`/`:8080` → `storageserv` using consistent hashing and **quorum-based Two-Phase Commit [2PC]** across fault-isolated zones) [S20, S21].
  - **How We Use It in `PS-01` (`F-06`, `ADR-0002`)**: We model our idempotent financial state store directly on `JunoDB`'s quorum key-value locking pattern, hashing `(workspace_id, tool_name, canonical_payload)` into a deterministic `PayPal-Request-Id` key with optimistic concurrency so no agent retry can ever double-charge, double-invoice, or double-refund.
- **`Apache Kafka` (Global Event Backbone)**: Processes **1.3+ trillion messages per day** at peak (21 million messages/sec) across **1,500+ Kafka brokers**, **85+ clusters**, **20,000+ topics**, and **~2,000 MirrorMaker nodes** at 99.99% availability—powering payment state transitions, webhook dispatch, and real-time risk graph ingestion [S25].
- **Sub-Millisecond Risk & HTAP Storage (`Aerospike`, `Redis Enterprise`, `Couchbase`, `TiDB`, `BigQuery`, `Elasticsearch`)**:
  - **Aerospike**: Flash/NVMe NoSQL store serving sub-millisecond velocity counters and device fingerprints to the fraud engine [S27].
  - **Redis Enterprise**: Powers PayPal's **Simility** risk engine to guarantee strict **read-after-write consistency** for active transaction risk sessions (replacing eventual-consistency Cassandra lag) [S28].
  - **TiDB (PingCAP)**: MySQL-compatible Raft HTAP database (`TiKV` + `TiFlash`) for horizontally scalable ledgers alongside **Oracle/MySQL**, **Apache Spark 3 + NVIDIA RAPIDS GPUs**, **Elasticsearch**, and **Google Cloud BigQuery** [S26, S29].

### 3. `Cosmos.AI` — PayPal's Enterprise MLOps, Envoy LLM Gateway & Decision DSL Platform
Documented by PayPal architects **Jun Yang, Zhenyin Yang, and Srinivasan Manoharan** (*"Scaling PayPal's AI Capabilities with PayPal Cosmos.AI"*, May 2024) [S26], **Cosmos.AI** comprises four core pillars that directly inspire our `PS-01` agent architecture (`ADR-0003`):
1. **Multi-Tenant `AI Projects` with RBAC**: Strict workspace isolation governing data lineage, model access, and auditability [S26].
2. **Envoy-Based Cosmos LLM Gateway**: Processes **hundreds of billions of tokens per day** across **100+ models** (OpenAI, Anthropic Claude, Google Gemini, NVIDIA Nemotron, vLLM, SGLang, Triton) via a unified TLS listener that enforces token budgets, rate limits, PII scrubbing, and automatic fallback routing [S26].
3. **Cosmos Decision Platform & Custom DSL Rule Engine**: In production at PayPal, probabilistic ML/LLM scores never mutate money directly; they feed into a **custom Domain-Specific Language (DSL) Rule Engine** that evaluates a **Directed Acyclic Graph (DAG)** of deterministic compliance, velocity, and risk rules [S26].
4. **How We Implement This in `PS-01` (`F-02`, `E-05`)**: Every `@paypal/agent-toolkit` tool call proposed by our LLM orchestrator (`M-01`) must first pass our **Deterministic `Cosmos.AI`-Style DSL Policy Firewall (`F-02`)**, which checks single-transaction caps, daily velocity, counterfactual risk score (`M-04`), and RBAC human-in-the-loop approval thresholds before touching the PayPal Sandbox.

### 4. Real-Time Graph Database, Mirror Graphs, GNNs, `gators` & Simility Fraud Engine
Documented by **Quinn Zuo, David Zhang, Yan Zhang, and Nitin Sharma** (*"How PayPal Uses Real-time Graph Database and Graph Analysis to Fight Fraud"*, PayPal Technology Blog) [S27]:
- PayPal models its 430M-account network as a heterogeneous graph where **vertices** are buyers, sellers, bank accounts, cards, devices, and IPs, and **edges** are transactions and shared attributes across three tiers: **Real-Time Graph** (sub-second online traversal), **Interactive Graph** (AML/investigator workbench), and **Analytics Graph** (offline Louvain/PageRank community detection) [S27].
- To prevent multi-hop neighbor explosion during online inference, PayPal invented **Mirror Graphs** that maintain pre-aggregated structural neighborhoods feeding **Graph Neural Networks (GNNs)** alongside **Simility** ($120M acquisition) and PayPal's open-source **`gators`** feature engineering library (`github.com/paypal/gators`, built on **Polars + ONNX Runtime**) [S27, S28, S67].
- **How We Implement This in `PS-01` & `PS-06` (`F-10`, `M-04`)**: We score every incoming dispute (`CUSTOMER.DISPUTE.CREATED`) and refund request using a **Multi-Hop Buyer-Merchant-Carrier Risk Graph (`M-04`)** powered by PyTorch Geometric + `gators` Polars/ONNX pipelines that links buyer dispute history, merchant fulfillment velocity, and verified carrier tracking (`get_shipment_tracking`) to distinguish legitimate customer issues from first-party friendly fraud.
